# DECISIONS.md

連番のDecision Log。単なる作業進捗は入れない。

## D001: 専用GitHubアカウント `0-isk-0` を使用する

- 背景: 開発者には別の個人プロジェクト群があり、Human OS Projectと相互に紐付くことを避けたい。
- 決定: Human OS Project専用のGitHubアカウント `0-isk-0` を使用し、SSH鍵・git identityもこのリポジトリ限定で分離する。
- 理由: 助成プログラムの成果物は大学・共有先に見える前提であり、他の私的プロジェクトと分離して運用したい。
- 代替案: 既存の個人アカウント内でリポジトリのみ分離する。
- 不採用理由: アカウントが同じだと、Human OS以外の活動が容易に辿れてしまう。
- 利点: プロジェクト間の切り離しが明確。
- 欠点: アカウント・鍵管理の手間が増える。
- 再検討条件: 特になし（現状維持で問題ない）。

## D002: Claude OS運用テンプレート（CLAUDE.md / docs分割 / rules / skills / agents）を導入する

- 背景: `CLAUDE.md`に恒久ルール・現在地・作業手順を混在させると、肥大化し`/clear`後の復元も難しくなる。
- 決定: `CLAUDE.md`は恒久ルールのみに絞り、目的・現在地・次作業・判断理由・運用・安全情報を`docs/`以下の個別ファイルへ分離する。作業手順は`.claude/skills/`、専門レビューは`.claude/agents/`に分離する。
- 理由: 会話履歴・コンテキスト圧縮に依存せず、リポジトリ内の正本ファイルだけで作業を再開できる状態を作るため。
- 代替案: 1つの巨大な`CLAUDE.md`にすべて詰め込む。
- 不採用理由: 肥大化により毎セッションのコンテキストを圧迫し、古い進捗情報が恒久ルールと混在して矛盾を生みやすい。
- 利点: 役割ごとにファイルが分かれ、古い情報の混入を防ぎやすい。
- 欠点: ファイル数が増え、初期構築の手間が増える。
- 再検討条件: 実際に運用してみて分割が過剰だと感じた場合、統合を検討する。

## D003: 新規SSH鍵は発行せず、既存の `id_github_isk` を使用する

- 背景: 当初「SSH鍵をゼロから発行する」想定で進めていたが、確認の結果 `~/.ssh/id_github_isk` が既に存在し、GitHubの`0-isk-0`アカウントへの認証にも成功した（`ssh -T github-isk` で確認済み）。
- 決定: 新規鍵を発行せず、既存の`id_github_isk`をそのまま`0-isk-0`用として使用する。
- 理由: 既に有効に動作している鍵を破棄して再発行する必要性がないため。
- 代替案: 想定通り新規鍵を発行し、古い鍵は削除する。
- 不採用理由: 既存鍵で認証が成功しており、鍵の入れ替えは不要なリスク（GitHub側の鍵再登録手順など）を増やすだけ。
- 利点: 手順が単純化された。
- 欠点: 鍵がいつ・どのセッションで作られたか正確な経緯が本人の記憶と一致していない（要注意点として記録）。
- 再検討条件: 鍵の作成経緯に疑義が生じた場合（意図しない第三者による作成等）は再発行を検討する。

## D004: プロダクトの方向性を「対話で更新され続ける・本人所有の人格モデル」の3層構造とする

- 背景: 「AIを作るのかMBTI的なものを作るのか」で構想が定まっていなかった。市場・文献調査3本といしこへのヒアリング2回を実施（`docs/plans/2026-07-31-initial-direction.md`）。
- 決定: 人格モデル（表現レイヤー）・対話アルゴリズム（取得レイヤー）・サービス（ループレイヤー）の3層構造を採用する。コンセプトは「対話するほど育つ、自分が所有する『自分の説明書』」。
- 理由: 調査の結果、AIとMBTIは二者択一ではなくレイヤーの違いであり、「本人が読めて・直せて・持ち運べる人格モデル」×「継続対話」の組み合わせは市場の空白地帯だった。Stanfordの研究（構造化インタビュー記録で本人回答を85%再現）が技術的裏付けになる。いしこのChatGPT壁打ち挫折（蓄積されない）への直接の解答にもなっている。
- 代替案: (a) MBTI型の一回きり診断サービス、(b) 診断構造を持たないAIコンパニオン、(c) PKM/メモツール型。
- 不採用理由: (a)は一回で消費されて終わる、(b)はReplika系の依存・規制リスクを引き受けるうえChatGPTと正面衝突する、(c)は「人はノートを再訪しない」というPKMの失敗パターンを繰り返す。
- 利点: 空白地帯であること、科学的足場があること、助成の研究発表と相性が良いこと、Phase 1がコストゼロで始められること。
- 欠点: 「人格モデルのスキーマ設計」という難易度の高い未知の問題を自分で解く必要がある。
- 再検討条件: Phase 1でいしこ自身の人格モデルv0を作った結果、本人が「これは自分だ」と感じられなかった場合はコンセプトから見直す。
- 決定者: いしこ（2026-07-31承認）

## D005: LLMエンジンは自作せず既存モデル（Claude）を借りる

- 背景: 「自分でAIを作るべきか」という論点があった。
- 決定: LLMエンジン（層①）は自作せず既存モデルを利用する。Human OSの本体は層②（人格モデル・対話アルゴリズム・記憶の設計）であり、そこに集中する。
- 理由: エンジン自作はゼロからで数十億円規模、ファインチューニングでも数十万円＋数ヶ月かかるうえ、出来上がりはClaude未満になる。先行サービス（Kin, Replika, Dot等）も全社エンジンは借りている。価値が宿るのはデータと対話設計の層である（Stanford研究の示唆）。
- 代替案: オープンモデル（Llama等）のファインチューニング。
- 不採用理由: コスト対効果が悪く、研究の本体（層②）から時間を奪う。
- 利点: コストほぼゼロで着手可能。人格モデルをポータブルに設計すれば、将来どのLLMにも差し替えられる（エンジン非依存こそが実質的に最も強い「自分のAI」）。
- 欠点: エンジンの挙動を完全には制御できない。API利用コストが発生する（少額）。
- 再検討条件: ローカルLLMの性能が用途に十分になった場合、プライバシー強化の選択肢としてエンジン差し替えを検討する。
- 決定者: いしこ（2026-07-31承認）

## D006: 初日（共有開始前）にGit履歴を初期化し、1コミットからやり直した

- 背景: D001の記述文（アカウント分離の理由説明）に、分離したかった対象（開発者の他の個人プロジェクトのアカウント名）を名指しで書いてしまい、Publicリポジトリに公開してしまった。さらに、すべてのコミットの作者メールアドレスに個人Gmailが記録されており、GitHubの「Commits」タブから直接見える状態だった。
- 決定: 該当コミット群を残さず、当時点のファイル一式（固有名・個人メールを除去済み）を1つの初期コミットとして積み直し、force pushでリモートの履歴を置き換える。以後は通常どおり細かくコミットする。
- 理由: リポジトリはこの日（2026-07-31）作成されたばかりで、URLは誰にも共有していない（教授・共同研究者への連絡はまだ送っていない）。この時点でのリセットは実質的な情報漏洩を伴わず、後から個別ファイルを修正するより確実に個人情報を除去できる。
- 代替案: (a) 修正コミットを積むだけで履歴は残す、(b) GitHub上でリポジトリを削除して新規作成する。
- 不採用理由: (a)は個人メールがコミット作者情報として残り続け解決にならない。(b)はリポジトリの削除操作自体が取り消せない別種のリスクを持ち、共有前のこの時点では過剰。
- 利点: 個人情報の完全除去。以後は「初日から細かくコミットする」という助成側の方針にクリーンな状態で従える。
- 欠点: 今日1日分の細かいコミット履歴（作業の刻み）は失われる。ただしこれは設計文書の整備段階であり、研究成果そのものの記録ではない。
- 再検討条件: なし。共有開始（教授・共同研究者への連絡）より後には、この種のリセットは行わない。
- 決定者: いしこ（2026-07-31承認）
