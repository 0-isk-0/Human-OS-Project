# 人格モデル v0 スキーマ（ドラフト）

ステータス: ドラフト。Phase 1でいしこ自身のモデルを1つ作りながら改訂する。

## 設計原則

1. **証拠リンク必須**: モデル内のすべての記述は、由来となったインタビュー発言（ログのID）に紐づく。AIの推測と本人の発言を区別する。
2. **本人確認済みフラグ**: 各項目は `unconfirmed`（AIが抽出しただけ）→ `confirmed`（本人が「そうだ」と認めた）→ `rejected`（本人が否定）の状態を持つ。confirmedのみが「モデル」を名乗れる。
3. **時間妥当性**: 人は変わる。各項目に記録日を持ち、古い項目は「当時の自分」として保持する（上書きではなく履歴化）。
4. **二重表現**: 内部＝構造化データ（JSON）、外部＝物語的な「自分の説明書」（Markdown）。内部から外部を生成する。
5. **ポータブル**: 特定のLLM・サービスに依存しない形式（JSON + Markdown）。いつでも持ち出せる。

## 4つの領域

ヒアリング（2026-07-31）でいしこが求めた4領域をそのままトップレベルに置く。

### 1. values — 価値観・判断基準

```json
{
  "id": "val-001",
  "name": "短い名前（本人の言葉を優先）",
  "statement": "何を大事にしているかの一文",
  "trade_off": "何と衝突したとき、どちらを取るか（判断基準の核）",
  "evidence": ["log-2026-08-01-023"],
  "status": "confirmed",
  "recorded_at": "2026-08-01"
}
```

- ラダリング（なぜ重要？の反復）で到達した終端が入る想定
- `trade_off` が重要: 「AとBどちらも大事」では判断支援に使えない。衝突時の優先が価値観の実体

### 2. thinking_patterns — 思考のクセ・認知パターン

```json
{
  "id": "tp-001",
  "pattern": "どういう考え方のクセか",
  "trigger": "どういう状況で発動するか",
  "effect": "それが助けになる場面 / 邪魔になる場面",
  "evidence": ["log-..."],
  "status": "confirmed",
  "recorded_at": "2026-08-01"
}
```

- レパートリーグリッド（本人固有の評価軸の抽出）の結果が主な供給源

### 3. goals — 目標・やりたいことの構造

```json
{
  "id": "goal-001",
  "statement": "何をしたいか",
  "layer": "vision | goal | project",
  "why": "上位の何につながるか（親goalのid、またはvalueのid）",
  "status": "confirmed",
  "recorded_at": "2026-08-01"
}
```

- 長期の夢（vision）→ 目標（goal）→ 具体的な活動（project）の3層。`why` で必ず上位につなぐ
- 上位につながらないgoalは「本当にやりたいのか？」を次回インタビューの問いにする

### 4. conditions — 感情・コンディションのパターン

```json
{
  "id": "cond-001",
  "state": "どういう状態か（調子が良い/悪い/散らかる等、本人の言葉で）",
  "trigger": "何がそれを引き起こすか",
  "sign": "その状態に入りかけているサイン",
  "recovery": "抜け出すのに効くこと（分かっていれば）",
  "evidence": ["log-..."],
  "status": "confirmed",
  "recorded_at": "2026-08-01"
}
```

## 付属構造

### open_questions — モデルの空白

AIがまだ分かっていないこと・矛盾して見えること。次回インタビューの問いの供給源。「モデルが育つ」感覚の中核。

```json
{
  "id": "oq-001",
  "question": "val-001とval-003は衝突しうるが、どちらが優先か未確認",
  "source": ["val-001", "val-003"]
}
```

### narrative — 自分の説明書（外部表現）

上記の構造化データから生成する物語的なMarkdown。「診断結果」として読める・見せられる形。生成物なので正本はJSON側。
