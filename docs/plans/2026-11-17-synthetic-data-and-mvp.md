## 1. このデータでできること／できないこと

### 1-1. 確認した事実（集計結果）

| # | 確認したこと | 数字 |
|---|---|---|
| a | 欠損がない完全な表 | 128人×100問＝12,800行、重複・空欄0件 |
| b | 回答日時がない | 時刻・セッション・順序の列が存在しない。全員が「1回だけ・一瞬で」答えた形 |
| c | 尺度80問は全問ほぼ同じ分布 | 全体平均3.01、各問の平均は2.76〜3.19。どの問いも「3」を中心に左右対称 |
| d | 逆転項目がない | `reverse_scored` は100問すべて `false` |
| e | 尺度80問は、回答者CSVにある**10個の隠し変数のどれか1つ**から作られている | 80問すべてが、いずれか1変数と r=0.56〜0.78 |
| f | 質問ファイル上の「テーマ」と、実際の回答のまとまりは一致しない | テーマ内の信頼性係数 α=0.22（価値観）〜0.73（思考）。8テーマ中6つが0.6未満 |
| g | 意味が反対の質問どうしが**正の相関**になっている | Q018「情報が十分でなくても進められる」× Q041「期待が曖昧だと負担」r=+0.47（両方に4以上が26人）。Q036「誤解は早めに確認したい」× Q038「本人に確認しないことがある」r=+0.53（同30人） |
| h | 場面選択10問は隠し変数とほぼ無関係な抽選 | 各選択肢24〜39人でほぼ均等 |
| i | 自由記述は1問あたり定型文3種類だけ | 1,280件の記述のうち、異なる文は30種類。同じ文を34〜54人が「書いて」いる |
| j | MBTIラベルは回答と無関係 | 隠し変数に対する説明率 η²=0.11〜0.20。無関係でも偶然出る期待値が0.118 |
| k | 10テーマのうち2つはほぼ空 | 「変化・自己認識」「目標・未来」は各2問（場面1・記述1）のみ。尺度は0問 |
| l | `answer_value` 列に数値（1〜5）と選択肢の文言が混在 | 場面選択は選択肢のIDではなく文言そのものを保存 |

### 1-2. ここから言えること

- **e・f・g の組み合わせが決定的**。回答は「質問の意味」ではなく「隠し変数」から作られていて、質問の向き（肯定／否定）も反映されていない。つまり**このデータの中の相関・まとまり・矛盾は、すべて生成プログラムの都合**であり、人の心の構造ではない。
- **j の注意点**: MBTI別に平均を出すと、差があるように見える変数が出る（不確実性耐性 η²=0.20）。これは8人ずつ16群に分けたときに偶然出る大きさ。**「少人数を多群に分けると、無関係でも差に見える」ことの実例**として、将来の実データ分析の戒めに使える。
- **c は実データでは起きない**（推測）。「目的が明確な仕事は取り組みやすい（Q053）」「小さな進捗が見えると続けやすい（Q055）」のような文は、実際の人はほぼ全員が4〜5を付けると予想される。合成データは全問を平均3に揃えているため、この問題が見えなくなっている。

### 1-3. できること

- 質問・回答者・回答を結合する処理、DBへの取り込み、画面表示、集計、エクスポート、削除の**動作確認**
- 128人分あるので、一覧・検索・ページ送り・速度の確認
- 「矛盾する回答の組を見つけて、条件を聞き返す」処理の**機械的な**テスト（g のおかげで矛盾ペアが大量にある）
- 尺度・場面選択・自由記述という3種類の回答形式を1つの保存形式で扱えるかの確認
- 隠し変数（＝正解）が分かっているので、集計コードが**計算として正しいか**の検算

### 1-4. できないこと

- 仮説の質の評価（「当たっているか」「役に立つか」）
- 質問の良し悪しの評価（どの質問が人を見分けるか、どれが誰でも「はい」になるか）
- 短縮版20問の選定（どの20問を選んでも、合成データ上では「うまくいった」ように見えてしまう）
- 基準率の算出（「この組み合わせは回答者の約◯%」という表示に、このデータの数字を使ってはいけない）
- 自由記述からAIが仮説を作る部分の検証（30種類の定型文しかないので、40人以上に同じ仮説が出るだけ）
- 本人の訂正でモデルが更新される流れの検証（訂正データが存在しない）
- 時間による変化の検証（時刻がない）
- MBTIと回答の関係についての一切の主張

## 2. Human OS の目的に対して足りない項目

### 2-1. 構造として丸ごと無いもの（最重要）

Human OS が記録したいのは「確認できた事実／AIの仮説／根拠／確信度／反証や矛盾／本人の修正／モデルの更新」の7つ。このデータにあるのは**最初の1つ（の材料）だけ**。

| 記録したいもの | このデータ | 必要なもの |
|---|---|---|
| 確認できた事実 | 回答そのもの（△） | 回答を「事実」として引用できるID、いつの回答か |
| AIの仮説 | 無 | 仮説テーブル（§6） |
| 根拠 | 無 | 仮説→事実のリンク |
| 確信度 | 無 | 仮説ごとのラベル |
| 反証・矛盾 | 無（矛盾する回答自体はある） | 仮説→反証のリンク、条件の記録 |
| 本人の修正 | 無 | 判定（合っている／違う／一部／言い換え）の記録 |
| モデルの更新 | 無 | 更新履歴（何が・いつ・なぜ変わったか） |

### 2-2. 質問側に足りない属性

| 足りないもの | なぜ要るか |
|---|---|
| 質問のバージョン | 文言を直したとき、過去の回答がどの文言への回答か分からなくなる |
| 選択肢のID | 今は文言で保存しているので、選択肢の表現を直すと過去データと繋がらなくなる |
| 層の区分（特性／内容／物語／現在環境） | D013により、**層によって言ってよいことが違う**。特性層の質問から来歴を語ってはいけない |
| 7領域との対応 | 既存の領域定義（D014）と繋がっていない |
| 質問の向き | 全問が肯定方向。何にでも「はい」と答える癖を検出できない |
| 「答えない」「場面による」の選択肢 | 全問が強制回答。`input-design.md` は答えない自由を前提にしている |
| いつの話か（今／以前） | 「過去から現在への変化」を扱うには、同じ質問を時期を変えて聞ける必要がある |
| 重さの区分 | 踏み込んだ質問を、本人が選んだときだけ出すため |

### 2-3. 回答側に足りない属性

回答日時／セッション／そのときの調子（シードQ4。回顧は回答時の気分で歪むため同時に記録する）／スキップしたかどうか／質問バージョン。

### 2-4. 内容として足りない・偏っているもの

1. **尺度80問のほぼ全部が「〜しやすい」「〜することが多い」型の自己記述**。これは4層のうち**特性層**であり、D013で「現在の記述に留める、来歴を語らない」と決めた層。v3が重心を置いた「今の暮らし（現在環境層）」に当たる質問は**0問**。
2. **「育った環境」に当たる質問も0問**。内容の来歴を語れる唯一の領域が入っていない。
3. **「過去から現在への変化」は実質2問**（Q084・Q098の自由記述）。目的に掲げている6項目のうち、最も手薄。
4. **価値観が「各価値を1問ずつ5段階で聞く」形式**（Q001〜Q010）。納得・貢献・意味・品質・自律はどれも「大事」と答えやすく、差がつかないと予想される（推測）。軸や理念を知りたい人にとって必要なのは「どれも大事なとき、どれを取るか」であり、**Q081型（二者択一）やシードQ13型（ペア比較）の形式が合う**。
5. **冒頭の問い（シードQ0「自分についていま一番知りたいことは？」）が無い**。出力を「本人の問いへの答え」として組み立てる起点が無い。
6. **誰でも当てはまりそうな文が多い**（推測）。Q012・Q016・Q028・Q050・Q053・Q055・Q064・Q071・Q075 など。これらに「5」と答えた事実から仮説を作ると、バーナム判定の②（誰にでも当てはまらないか）に落ちる。実データで分布を見るまで確定できない。

### 2-5. 逆に、100問側にあって既存のシード20問に無いもの

「学習・成長」「動機・行動」（計24問）。目的に掲げた「どんな方法なら学習や行動を続けやすいのか」は、既存の7領域のどこにも正面から入っていない。

**扱い（D019）**: 8つ目の領域にはしない。**「学び方・続け方」というタグ**を付け、最も近い領域（決め方／これからのこと）の深掘りの中で出す。領域にするかは Phase 0 の後に検討する（H5）。

### 2-6. 使える部分

**Q081〜Q100 の20問（場面選択10・自由記述10）は質が高い**。具体的な場面や最近の出来事を聞いており、事実ログの材料になる。特に Q097・Q098 は「自分についての説明がしっくりこないときどうしたいか」「見立てを訂正した経験」を聞いていて、**訂正フローの入口の文言としてそのまま使える**。

### 2-7. 100問の選別結果（深掘り候補）

**選別の根拠は質問の文面だけ**であり、合成データの数字は使っていない（使えない。§1-4）。「誰でも当てはまりそう」という判定は推測で、実回答で確かめるまで確定しない（H6）。質問文つきの全表は `.local/question-bank/screening-2026-11-17.md`（H2 により公開リポジトリには置いていない）。

基準:
1. 7領域のどれかに入るか
2. 4層のどれに当たるか（特性層の質問からは来歴を語れない。D013）
3. 人によって答えが分かれそうか（誰でも「はい」になる質問は、バーナム判定の②に落ちる仮説しか生まない）
4. 具体的な場面や出来事を聞いているか（事実ログの材料になるか）

| 区分 | 件数 | 質問番号 | 使い方 |
|---|---|---|---|
| **A. 深掘りの第一候補** | 18 | Q081〜Q096、Q099、Q100 | 場面選択と自由記述。深掘りで最初に出す |
| **B. 仮説を確かめる補助** | 39 | Q007 Q015 Q018〜Q021 Q023〜Q027 Q030 Q032 Q034〜Q036 Q038 Q039 Q041 Q043〜Q046 Q048 Q049 Q051 Q052 Q056〜Q058 Q068〜Q070 Q072〜Q074 Q077 Q078 Q080 | 尺度。確信度の低い仮説を確かめるときだけ1〜2問出す |
| **C. 形を変えれば使える** | 5 | Q001 Q002 Q003 Q008 Q009 | 価値観を1つずつ5段階で聞く形をやめ、「どちらを取るか」の対にする |
| **M. 質問としては出さない** | 2 | Q097 Q098 | 判定画面の文言・訂正の導入に使う |
| **D. 見送り** | 36 | 上記以外 | 下の理由 |

見送りの理由:
- ほぼ誰でも「当てはまる」と答えそう（30問）。例: Q053「目的や完成条件が明確な仕事は、取り組みやすい」
- 「そうありたい姿」を聞いていて、望ましい方に答えが寄りそう（6問）。例: Q033「意見が違っても、尊重して話し合える関係を大切にする」

B のうち**対で使うもの**（反対向きの2問を両方聞き、両方に「当てはまる」なら条件を聞き返す）: Q018×Q041、Q023×Q024、Q036×Q038、Q051×Q052、Q068×Q069、Q049×Q035。Q044 はシードQ3（今どれくらい自分で決められるか）と組で使う。

選別後（A＋B＋C＝62問）の領域別の数:

| 領域 | 候補数 | 層 |
|---|---|---|
| 1 今の暮らし | **0** | — |
| 2 調子の波 | 25 | 特性（記述4問は物語） |
| 3 人との距離 | 8 | 特性 |
| 4 決め方 | 11（うちタグ「学び方・続け方」5） | 特性 |
| 5 大事にしていること | 8 | 内容 |
| 6 育った環境 | **0** | — |
| 7 これからのこと | 10（うちタグ「学び方・続け方」8） | 物語・特性 |

**読み取れること**:
- 候補は「調子の波」に偏る（62問中25問）。「感情・回復」「ストレス・負荷」「能力発揮環境」の3テーマがすべてここに入るため。
- v3 が重心を置く「今の暮らし」と、来歴を語れる「育った環境」は、選別しても0問。**この2領域の深掘りは100問からは作れない**ので、必要になったら別に作る。
- 特性層が大半。ここから作れる仮説は「今こうである」の記述までで、「なぜそうなったか」は書けない。
- シード20問と内容が重なる質問がある（Q085≒シードQ12、Q087≒Q9、Q088≒Q8、Q090≒Q7、Q100≒Q20）。同じことを続けて聞かず、「選択式で答えたことを、出来事で確かめる」順で使う。

## 3. 合成データ本体を使わずに試作する方法

D019 により、128人×100問の本体は公開リポジトリに入れない。代わりに次の2つを使う。

### 3-1. 案A: 生成スクリプト（件数が要る確認用）

- リポジトリに置くのは**スクリプトだけ**。出力は `.local/`（Git管理外）に作る。
- 乱数の種を固定し、同じ種なら同じデータが出るようにする。
- 元のデータに無かったものを最初から入れる: 回答日時・セッション・スキップ・選択肢のID・質問の向き・**判定（合っている／一部／違う／言い換え／保留）**。
- MBTI列は作らない。検算用の隠し変数は別ファイルに出し、製品側のテーブルには入れない。
- 元のデータに生成スクリプトは同梱されていなかったので、新しく書く（同じ128人を再現するものではない）。

### 3-2. 案B: 手書きの架空サンプル（中身の確認用）

- 架空の人物3〜5人が、**シード20問＋Q0**に答えたもの。自由記述は人ごとに違う内容で書く。
- 量が少なく、個人情報も質問バンクの文面も含まないので、リポジトリに置ける（`data_origin=synthetic` と明記）。
- AI の仮説生成・バーナム判定・判定画面の確認に使う。元の合成データは自由記述が定型文30種類しかなく、この用途に使えない。

### 3-3. 使い分け

| 確かめたいこと | 使うもの |
|---|---|
| 保存・表示・判定・更新履歴・書き出し・削除が動くか | 案B（先に作る） |
| AI の仮説が規則を守るか | 案B |
| 一覧・検索・件数が多いときの速さ | 案A |
| 矛盾の検出と聞き返し | 案A（反対向きの対に両方「当てはまる」人を意図的に作る） |
| 役に立つか・当たっているか | どちらでも分からない。開発者自身の回答（Phase 0）から |

元の128人×100問は `.local/synthetic-128x100/` に置いてあり、構造の参考としてだけ使う。

### 3-4. 守ること（コードで強制する）

1. `data_origin` 列を全テーブルに持たせ、`synthetic` と `real` を同じ集計に混ぜない。
2. 検算用の隠し変数は製品のテーブルに取り込まない。
3. 架空データから作った仮説を、質問の改善や選別の根拠にしない。
4. 画面に出す「回答者の約◯%」のような数字を、架空データから計算しない。

## 4. 実際の参加者からデータを集める際の設計

**前提（D017）**: 開発者以外からデータを集める前に、倫理審査の承認か正式な適用除外が必要。友人ミニテスト（Phase 1）が対象に入るかは `[要確認]` のまま。**以下は審査に出す設計案であり、承認までは実施しない。**

### 4-1. 同意

- 同意は**用途ごとに分ける**（まとめて1つにしない）: ①回答を保存する ②回答をAIに渡して仮説を作る ③匿名化した集計を研究報告に使う ④自由記述を言い換えて引用する。①②が無いと利用できない。③④は断っても利用できる。
- 同意文にはバージョンを付け、誰がどの版に同意したかを記録する。
- いつでも撤回でき、撤回したら§4-3の削除が走る。
- 説明に必ず入れること: 医療・心理診断ではない／AIの出力は仮説であり誤りうる／回答はAI（Claude）に送られる／答えたくない質問は飛ばせる／つらくなったら中断でき、相談先を示す。
- 対象は18歳以上。

### 4-2. 匿名化

- 回答のテーブルには氏名・メール・学籍番号を置かない。参加者はランダムなIDで識別する。
- ログイン情報と回答を結ぶ対応表は別テーブルに分け、研究用の書き出しには含めない。
- 属性は粗い区分のみ（年齢帯など）。合成データの `age_band` の粒度が目安。
- **自由記述は匿名化できないものとして扱う**（固有名詞や出来事から本人が分かる）。集計・共有の対象から外し、本人の画面にだけ出す。
- 少人数の集計は出さない（例: 5人未満の区分は表示しない）。

### 4-3. 保存・削除

- 保存場所は1か所に決める。Worker側のD1は「再利用可能なリクエストの型だけを保存し、会話は保存しない」設計なので、**回答を保存するDBは別に用意する**。D1に置くかどうかを含め、設計は別途検討する（H4）。Phase 0 は手元のファイルに保存し、外部には置かない。
- 公開リポジトリには実データを一切置かない（既存ルール）。
- 本人による**書き出し**（全データをJSONで）と**削除**（関連行を全部、復元不能に）を Phase 0 版から含める。「本人所有」の実体はこの2つ。
- 保存期間を決める（案: 助成期間終了の2027-05-01まで。延長は再同意）。
- `[要確認]`: 大学の Claude Enterprise の利用条件で、参加者の回答を入力してよいか。倫理審査の質問と一緒に確認する。

### 4-4. 共有

- 既定は本人のみ。開発者も、③の同意がある人の集計値しか見ない。
- 個別の回答・仮説を指導教員等と共有する場合は、その都度の同意を取る。
- 本人が自分の説明書を他人に見せる機能は後回し（§5）。

### 5-2. 後回し

| 機能 | 後回しの理由 |

### 5-3. 短い入口と深掘りの組み合わせ方

```
[入口] Q0 ＋ シード20問（3分）──→ 仮説3〜5件
                                   │
          本人が判定 ←─────────────┘
              │
   ┌──────────┼──────────────┐
合っている    一部／言い換え     違う
   │            │               │
確信度↑     本人の言葉で置換    却下として保存
   │            │               │
   └─────┬──────┴───────────────┘
         │
  [深掘り・任意] 気になる仮説を選ぶ
         → その領域の A（場面・記述）から2〜3問
         → 確信度が低ければ B（尺度）から1〜2問
         → 仮説を更新、または新しい仮説
```

深掘りの質問は §2-7 の選別結果から引く。「今の暮らし」「育った環境」には候補が無いので、当面この2領域はシードの回答だけで扱う。

## 6. データベース設計案

**Phase 0 は手元のSQLiteファイル（`.local/` の中、Git管理外）に作る。** 他の人が使う段階の保存先（D1 を含む）は別途検討する（H4）。SQLite の書き方にしてあるので、後で移すときに表の形は変えずに済む。`consents` は Phase 0 では使わない。元の合成データのCSV列との対応を右に示す。

```sql
-- 参加者。氏名・メールは持たない
CREATE TABLE participants (
  id            TEXT PRIMARY KEY,           -- ランダムID        ← respondent_id
  data_origin   TEXT NOT NULL CHECK (data_origin IN ('synthetic','real')),  ← data_origin
  age_band      TEXT,                       --                   ← age_band
  created_at    TEXT NOT NULL
);

-- 同意（用途別・版つき・撤回可）。synthetic には不要
CREATE TABLE consents (
  id TEXT PRIMARY KEY, participant_id TEXT NOT NULL REFERENCES participants(id),
  consent_version TEXT NOT NULL,
  scope TEXT NOT NULL CHECK (scope IN ('store','ai_process','research_aggregate','quote_paraphrased')),
  granted_at TEXT NOT NULL, withdrawn_at TEXT
);

-- 質問（文言を直したら version を上げ、古い行は残す）
CREATE TABLE questions (
  id TEXT NOT NULL, version INTEGER NOT NULL,              -- ← question_id
  domain TEXT NOT NULL,      -- 7領域
  theme TEXT,                --                              ← theme
  dimension TEXT,            --                              ← dimension
  layer TEXT NOT NULL CHECK (layer IN ('trait','content','narrative','present_env')),
  response_type TEXT NOT NULL,  -- likert_1_5 / single / multi / pair / open_text   ← response_type
  prompt TEXT NOT NULL,      --                              ← prompt
  direction INTEGER NOT NULL DEFAULT 1,   -- 1 / -1          ← reverse_scored
  time_frame TEXT NOT NULL DEFAULT 'now', -- now / past
  weight_class TEXT NOT NULL DEFAULT 'light',  -- light / heavy（踏み込み度）
  is_seed INTEGER NOT NULL DEFAULT 0,
  active INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY (id, version)
);

CREATE TABLE question_options (
  id TEXT PRIMARY KEY, question_id TEXT NOT NULL, question_version INTEGER NOT NULL,
  position INTEGER NOT NULL, label TEXT NOT NULL            -- ← options[]
);

-- 回答の1回分のまとまり
CREATE TABLE sessions (
  id TEXT PRIMARY KEY, participant_id TEXT NOT NULL REFERENCES participants(id),
  mode TEXT NOT NULL,          -- seed / deep_dive
  mood_2w INTEGER,             -- シードQ4（回顧の歪みを後から見るため）
  started_at TEXT NOT NULL, finished_at TEXT
);

-- 回答。合成データでは answer_value に数値と文言が混在していたので、型別の列に分ける
CREATE TABLE responses (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL REFERENCES sessions(id),
  participant_id TEXT NOT NULL REFERENCES participants(id),
  question_id TEXT NOT NULL, question_version INTEGER NOT NULL,
  scale_value INTEGER,         -- 尺度                      ← answer_value（数値）
  option_id TEXT,              -- 選択                      ← answer_value（文言→ID）
  text_value TEXT,             -- 自由記述                  ← answer_text
  skipped INTEGER NOT NULL DEFAULT 0,
  answered_at TEXT NOT NULL,
  data_origin TEXT NOT NULL    --                           ← data_origin
);

-- 確認できた事実。回答・本人の発言・出来事を、仮説から引用できる形にしたもの
CREATE TABLE facts (
  id TEXT PRIMARY KEY, participant_id TEXT NOT NULL REFERENCES participants(id),
  source_type TEXT NOT NULL CHECK (source_type IN ('response','utterance','event')),
  source_id TEXT,              -- responses.id など
  content TEXT NOT NULL,       -- 「Q9で〈自分の要望を引っ込める〉を選んだ」
  refers_to_period TEXT,       -- いつの話か
  recorded_at TEXT NOT NULL
);

-- AIの仮説。上書きしない。直すときは新しい行を作り superseded_by で繋ぐ
CREATE TABLE hypotheses (
  id TEXT PRIMARY KEY, participant_id TEXT NOT NULL REFERENCES participants(id),
  domain TEXT NOT NULL, layer TEXT NOT NULL,
  statement TEXT NOT NULL,          -- 仮説の一文
  conditions TEXT,                  -- 当てはまる状況／当てはまらない状況
  confidence TEXT NOT NULL CHECK (confidence IN ('low','medium','high')),
  status TEXT NOT NULL DEFAULT 'unconfirmed'
    CHECK (status IN ('unconfirmed','confirmed','partial','rejected','on_hold')),
  authored_by TEXT NOT NULL CHECK (authored_by IN ('ai','person')),
  alternative_of TEXT REFERENCES hypotheses(id),  -- 同じ事実に対する別の説明
  superseded_by TEXT REFERENCES hypotheses(id),
  barnum_check TEXT,                -- 4基準の結果（JSON）
  model_id TEXT, prompt_version TEXT,  -- どのAI・どの指示で作ったか（再現のため）
  created_at TEXT NOT NULL
);

-- 根拠と反証
CREATE TABLE hypothesis_evidence (
  hypothesis_id TEXT NOT NULL REFERENCES hypotheses(id),
  fact_id TEXT NOT NULL REFERENCES facts(id),
  role TEXT NOT NULL CHECK (role IN ('support','counter')),
  PRIMARY KEY (hypothesis_id, fact_id)
);

-- 本人の判定
CREATE TABLE judgments (
  id TEXT PRIMARY KEY, hypothesis_id TEXT NOT NULL REFERENCES hypotheses(id),
  verdict TEXT NOT NULL CHECK (verdict IN ('agree','partial','disagree','restate','hold')),
  restatement TEXT,            -- 本人の言い直し
  comment TEXT,
  judged_at TEXT NOT NULL
);

-- モデルの更新履歴
CREATE TABLE revisions (
  id TEXT PRIMARY KEY, hypothesis_id TEXT NOT NULL REFERENCES hypotheses(id),
  trigger_type TEXT NOT NULL,  -- judgment / new_fact
  trigger_id TEXT,
  change TEXT NOT NULL, reason TEXT NOT NULL,
  revised_at TEXT NOT NULL
);

-- タグ（領域にしない切り口。例: 学び方・続け方）
CREATE TABLE question_tags (
  question_id TEXT NOT NULL, tag TEXT NOT NULL,
  PRIMARY KEY (question_id, tag)
);

-- 検算専用。製品のコードからは読まない
CREATE TABLE fixture_synthetic_latents (
  participant_id TEXT PRIMARY KEY, mbti_label TEXT, latents_json TEXT, persona_seed INTEGER
);
```

既存の `personality-model-v0.md`（v0.3）との関係: 3層（事実ログ・仮説・更新履歴）はそのまま引き継いだ。`golden_mean`・`trajectory`・`name_light/name_shadow` は却下済みの方針v2由来の項目なので Phase 0 版では持たない（必要になれば列を足す）。

## 7. AI が仮説を作り、本人の訂正で更新する対話フロー

### 7-1. 手順

1. **問いを立てる**（Q0）。以後の出力はこの問いへの答えとして組み立てる。
2. **回答する**（シード20問）。
3. **事実にする**。回答を解釈せずにそのまま文にする（「Q9で〈自分の要望を引っ込める〉を選んだ」）。ここにはAIの推測を入れない。
4. **仮説を作る**。AIへの指示で次を必須にする:
   - 根拠の事実IDを2件以上挙げる（挙げられない仮説は出さない）
   - 同じ事実を説明する**別の仮説を1つ以上**並べる
   - 確信度を付け、その理由を書く（根拠が2件・同じ領域のみなら low）
   - 層を守る: 特性層の事実からは「今こうである」までしか言わない。「〜だからこうなった」を書かない（D013）
   - バーナム判定4基準を通す。落ちたものは出さない
5. **1件ずつ見せる**。本人が明らかに同意しそうなものから先に出す（`explanation-design.md` の提示順）。各仮説の下に根拠の回答を表示する。
6. **本人が判定する**:
   | 判定 | モデルの更新 |
   |---|---|
   | 合っている | status=confirmed、確信度を上げる |
   | 一部合っている | 「どの部分が／どんなときは違う？」を1問聞く → `conditions` に記録、status=partial |
   | こう言い換えたい | 本人の文で新しい仮説を作り（authored_by=person）、元の仮説は superseded_by で繋いで残す |
   | 違う | status=rejected。**より広い言い方に言い換えて出し直さない**（CLAUDE.md の出力規則）。任意で「どこが違うか」を聞き、事実として記録 |
   | 今は決めない | status=on_hold。「まだ分からないこと」に入れる |
7. **矛盾を拾う**。支持する事実と反証が両方ある仮説は、矛盾として隠さず「どんなときはA、どんなときはB？」と条件を聞く。答えは `conditions` へ。
8. **履歴に残す**。6・7 のすべてを `revisions` に書く。
9. **次の入口を出す**。「まだ分からないこと」から、深掘りできる領域と質問数を示す（任意）。

### 7-2. 架空データでの通し確認の例

生成スクリプト（§3-1）で、反対向きの対（Q018 と Q041）の両方に4以上を付けた架空の人を作って使う。
- 事実: 「Q018『情報が十分でなくても仮の結論を置いて進められる』に4」「Q041『期待が曖昧な状況は負担になりやすい』に5」
- 仮説A: 「自分で決められる曖昧さは平気で、人からの期待が曖昧なときに負担が出る」
- 仮説B（別の説明）: 「進めることはできるが、その間ずっと負担は感じている」
- 判定を乱数で発生 → 更新と履歴が正しく積まれるかを確認

**これは流れが動くかの確認であり、仮説の中身に意味は無い**（§1-2 のとおり、この矛盾自体が生成プログラムの産物）。
